# Long tokens: Office evidence and rule contract

P1 item 1 is closed for **basic Latin letters/digits in ordinary ungrouped,
horizontal text shapes**, not for universal text shaping or line breaking.

The original hypothesis was a missing horizontal error. Opening the fixture
in PowerPoint showed a different result: with word wrap enabled, an overlong
Latin word breaks by character even when `latinLnBrk` is absent or false.
Consequently, a tall box is clean, while the same text in a short box runs out
the bottom. Simply enabling `PPT003` on the old unbroken-word measurement would
have produced false positives for the clean controls.

## Evidence

- Renderer: **Microsoft PowerPoint for Mac 16.112.3**, macOS Apple Silicon.
- Observed locally on 2026-09-06, without editing or resaving the input.
- Input: [`corpus/pptx-long-tokens.pptx`](../corpus/pptx-long-tokens.pptx),
  SHA-256 `ada1bc9ae01fb0a7aed97e7f351b6e4f3075a9a5a3b20a1b182f36fcf9ad440c`.
- Export: native **File → Export → PNG → Save Every Slide**, 960 × 540.
  Every exported slide was inspected individually at full size. No repair
  prompt appeared. The committed PNGs are actual Office exports, not renders
  generated by the checker or its fixture-authoring tool.
- Text: real Calibri at 24pt, except slide 11's stored 50% shrink (12pt).
  The model resolves the installed Office face exactly on this machine.
- Provenance and image hashes: [`evidence.json`](calibration/pptx-long-tokens/evidence.json).
  The fixture and exports contain only synthetic text, under the project's MIT
  licence; no Office fonts or personal document content are redistributed.

Each slide has one native text box. Its blue outline is the actual shape
boundary; no separate label or decorative shape affects the check. The main
box is 120pt wide with zero insets. Slide 10 adds 20pt left/right insets; slide
8 is 9pt wide. The input was authored with `@oai/artifact-tool`, then explicit
test settings were applied to the OOXML (`latinLnBrk`, insets, `fontScale`).
Structural, geometry, font-policy and import checks passed before opening it
in PowerPoint. Intentional overflow was preserved.

All 12 line counts **and the actual strings on each line** match the new
model. The preceding implementation found only slide 6; it missed slides 2,
8 and 10. Eight clean controls remain free of WARN/ERROR findings.
The two short boxes are 40pt high: the old one-line estimate (28.8pt) fits,
whereas the actual four/seven-line rendering does not. Running the checker
from commit `8f961a4` against this exact fixture confirms the three omissions.

The prefix controls matter: default wrapping moves the word onto a new line;
`latinLnBrk=1` uses the remaining space after `Hi`. The Office default of false
is also documented in Microsoft's
[DrawingML implementation notes](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/e05f6e35-a35d-4f00-924f-8172fe339bf5).
The emergency wrap and exact line breaks above are renderer observations,
not assumptions inferred solely from that specification.

## Confidence, severity and remediation

- `PPT001`: supported character wrapping adds lines; if their needed height is
  more than 5% beyond the usable height, report ERROR with trustworthy font
  metrics. Existing `PPT002` height tolerance remains unchanged.
- `PPT003`: after supported wrapping, a single glyph may still exceed the
  available width. More than 5% horizontal excess produces ERROR with
  trustworthy metrics. With wrap off, the existing whole-line rule is retained.
- A character-break decision within 5% of the width boundary downgrades the
  result to an estimate/WARN. Approximate fonts do the same. Unsupported
  overlong tokens (other scripts, combining sequences, URLs/punctuation-aware
  breaking) are retained as unbroken estimates, with an explicit note requiring
  renderer verification, never a confident ERROR. Coverage cannot call these
  exact-font-but-approximate layouts `checked`.
- `normAutofit` without a stored shrink remains `PPT005` WARN; `spAutoFit`
  retains its existing exclusion. This change does not settle the separate
  renderer-dependent autofit policy.
- Findings identify `slideN/shape-name`. Fix the content or geometry: widen the
  box, add height for the extra lines, reduce font size, or introduce deliberate
  break points. Turning wrap on is insufficient when even one glyph is too
  wide. Verify the corrected slide in the target Office renderer before
  suppressing an estimate; the checker does not edit the presentation.

The regression suite additionally uses deterministic metrics for exact/near
boundaries, zero width, paragraph indent, mixed sizes/styles, legacy kerning,
hard breaks and trailing spaces, missing/fallback fonts, inheritance and
linear-time handling of a 10,000-character token. These unit tests are not
misrepresented as additional Office observations.

## Limits

This is one Office build and font, not Windows/web validation, independent
human review or a statistically broad rendering study. The original
`corpus/deck.pptx` and its calibration remain unchanged. Unicode grapheme
breaking, hyphenation, tabs, language-specific punctuation, complex shaping,
group/rotation transforms and advanced text owners remain outside this change.
The broader wrapping row in the support matrix therefore remains **Partial**.
