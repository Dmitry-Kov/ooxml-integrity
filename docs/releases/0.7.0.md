# ooxml-integrity 0.7.0

Release candidate. A new rule, `PKG010`, reports a file Word refuses that no
earlier rule did, and a new command, `fix`, writes a re-checked copy with the
three repairs whose result is unique. Python 3.9+, dependencies and the MIT
license are unchanged. The project remains research-alpha.

## A content type Word refuses: `PKG010`

A Word for Mac check of repaired benchmark copies found that Word refuses all
five Codex outputs of the review-history benchmark's K5-S1 task as unreadable,
while LibreOffice opens them. The cause is one value: the `commentsExtended`
part is declared `application/vnd.ms-word.commentsExtended+xml`, not the type
its relationship requires. With only that value corrected, Word opens the file.
The frozen oracle counts the five outputs as correct; the finding is recorded
post hoc, next to the earlier Word check
([Word check](../../evidence/review-history-benchmark/word-check-content-type/README.md)).

- `PKG010` (ERROR) reads the parts the main document relates through fifteen
  relationship types and reports a part whose declared content type is not the
  one its relationship type requires. Letter case and parameters are not
  reported; a missing part or a part without a content type stays with
  `REL002` and `PKG005`; templates, macro-enabled documents and Strict are not
  read.
- Across 3,283 files in this repository and the public corpora it fires on
  those five outputs only, and every other finding is unchanged
  ([run](../../evidence/docx-content-types/README.md)).
- Coverage gains `package.related-content-types`, which says when the main part
  was not read.

## Repairing what has one answer: `fix`

```sh
ooxml-integrity fix edited.docx -o repaired.docx
```

`fix` makes only repairs whose result is unique and provable by checking
again; it never restores or invents content, and lists every finding it did not
repair with the reason ([fix](../fix.md)).

- **anchor-replies** (`CMT005`): a reply whose parent comment is anchored gets
  its parent's range, in the order Word writes a thread.
- **renumber-revisions** (`REV001`): every repeated revision id after the first
  gets a fresh id.
- **content-type** (`PKG010`): a related part's `Override` gets the content
  type its relationship type requires. A part typed only by a `Default` is
  refused, since changing the `Default` would retype other parts.

The copy is written to a temporary file, checked again with `check` and
`compare` (and against `--against SOURCE`), and renamed only when every
targeted finding is gone and nothing new appeared. Only the repaired bytes
change; every other ZIP member is copied as stored. Exit codes: `0` repaired
and verified, `1` nothing written because nothing could be repaired, `2` usage
error or a package `fix` does not rewrite, `3` the re-check failed.

On the repository's 51 DOCX with one of the three findings, 29 were repaired
and 22 refused with their reasons
([evidence](../../evidence/fix-repairs/README.md)). Word for Mac 16.113.4 shows
each repaired reply in its parent's thread and treats renumbered revisions
exactly as the originals; from the Codex output it refused, `fix` writes the
copy Word opened, byte for byte.

## The MCP server's config

An outside audit found that `ooxml-integrity mcp` read the project config on
every call from the repository the agent edits, so the agent could write an
`[[ignore]]` for the finding it caused. The server now reads the config once,
when the client starts it; a later change is not applied, and the verdict says
the config changed since the server started. The verdict names every finding a
config suppressed and the file. The [guide](../mcp.md) says how to run a check
the agent cannot influence.

## Other changes

- The package ships `py.typed`.
- CI also runs on Windows with Python 3.9 and 3.14; CPython 3.14 for Windows
  deflates with zlib-ng, so the byte-for-byte fixture rebuilds skip there.
- docx-cli fixed the two issues this project reported (numeric character
  references, tracked replace inside another author's insertion) on its main
  branch; the README table says so.

## Compatibility

- `PKG010` is a new ERROR: a document that passed the default gate can exit 1.
  Among the corpora that happens only to the five Codex outputs Word refuses.
  A project that accepts such files can lower or turn off the rule with a
  reason. Its baseline v2 identity is file, code and part; coverage schema 1
  gains an identifier, which consumers must tolerate.
- `fix` is a new command; its `--json` has no schema version yet.
- The MCP server, which has no contract of its own yet, reads its config once;
  restart it to apply a config change.
- Other rule codes, severities, messages, report fields, Doctor schema 1,
  SARIF 2.1.0, CLI exits 0/1/2 and baseline v2 identities are those of 0.6.0.
  JSON/Doctor package version becomes `0.7.0`. See the
  [compatibility policy](../compatibility.md).

## Validation and publication

[Candidate validation](../../evidence/releases/0.7.0/README.md) passed:
2330 tests with 7 documented skips, on Python 3.12 and 3.14, the
suite run from the unpacked sdist (2302 passed, 35 skipped), the 220-pair
producer corpus, 30 revision pairs and 168 stored editor output pairs, the
frozen checker replay, the four comment-story pairs, reference-deck assertions,
a rerun of the anonymize measurement with the same result, strict wheel/sdist
metadata checks and both fresh installations, plus all 7 real Chromium/Pyodide
scenarios against the exact local candidate wheel. The installed-package smoke
adds the 0.7.0 controls: `PKG010` on a Codex output, and `fix` repairing it to
a copy on which the checker finds nothing. No new Office, agent or model run
was part of release packaging. Local candidate and later
publication hashes are separate records.

After candidate checks pass, CI must pass on the exact merged main commit before
tagging. The Release workflow then verifies the remote pinned Action, rebuilds
and tests distributions, publishes those files to PyPI, and creates the GitHub
Release. Public PyPI installation/hash verification and consumer/demo pin updates
follow publication. See [release procedure](../releasing.md).

Use these pins **after publication**:

```sh
python -m pip install --upgrade ooxml-integrity==0.7.0
python -m ooxml_integrity --version
```
