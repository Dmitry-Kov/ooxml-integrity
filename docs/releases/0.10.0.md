# ooxml-integrity 0.10.0

Published 2026-11-10T09:14:35Z on [PyPI](https://pypi.org/project/ooxml-integrity/0.10.0/)
and as a [GitHub Release](https://github.com/Dmitry-Kov/ooxml-integrity/releases/tag/v0.10.0). `--introduced`
fails a comparison only on findings the edit added, `CMT007` reports a comment
marked more than once in a story, and `FID015` and `FID016` report the
bookmarks and fields an edit lost against its source. `server.json` describes the MCP server for catalogs. A document or a
comparison that passed can now fail, hence the minor version. Python 3.9+,
dependencies and the MIT license are unchanged. The project remains
research-alpha.

## Only what the edit added: `--introduced`

`check --against` reported every finding of the edited copy, including those
its source already had, so an edit of a document that arrived with an orphaned
comment failed for damage it did not do. A baseline cannot cover that when
every run brings another document, as when an agent edits whatever a user
uploads.

- **`--introduced` checks the source too.** A finding the source already has,
  same code, part and message, counted, is suppressed with the reason
  `already in the source (--introduced)`: in `--show-suppressed`, in the JSON
  report's `suppressed` list and in SARIF. Positions are not compared, since an
  inserted paragraph moves every later XPath; when the edited copy has more of
  a finding than the source, the ones reported are those at a location the
  source does not have.
- **Never set aside:** lost or changed content (`FID`), a check that did not
  complete (`INT001`), an expectation (`EXP001`), and every finding that says
  part of a file was not checked (`PKG000`–`PKG002`, `PKG006`–`PKG009`,
  `XML001`, `CMT006`, `PPT000`). A source that cannot be read absorbs nothing.
- **The same in every interface.** `introduced()` in Python,
  `"introduced": true` on the MCP `compare` tool and `introduced: "true"` in
  the Action. Without `--against` the flag is a usage error (exit 2).
- **What it cannot tell.** `TBL001` and `TBL002` name the table and row by
  number, so a table inserted earlier makes an inherited table finding look
  new, and the run fails. An edit that fixes one finding and causes another
  with an identical message balances the count and reports nothing
  ([what counts as the same finding](../configuration.md#defects-the-source-already-had)).

```sh
ooxml-integrity check edited.docx --against original.docx --introduced
```

## A comment marked more than once: `CMT007`

- `CMT007` (ERROR, `check()`) reports a second `commentRangeStart`,
  `commentRangeEnd` or `commentReference` for one comment id in a story. Every
  start still had an end and a reference, so `CMT001` to `CMT003` passed such
  a file, and against its source it was only `FID002` INFO
  (`comment anchors: 1 -> 2`).
- The closed python-docx
  [PR #1605](https://github.com/python-openxml/python-docx/pull/1605) writes it
  when `Paragraph.text` is set on the first paragraph of a comment that spans
  two: the end and the reference again, while the second paragraph keeps its
  own.
- Markers in a later branch of `mc:AlternateContent`, where Word repeats a text
  box for older readers, are copies and do not count. A comment anchored once
  in each of two stories is not reported.
- None of 1,903 public Word files and no file in this repository has one. Such
  a file was not opened in Word.

## Bookmarks and fields against a source: `FID015`, `FID016`

"See clause 4.2" is a `REF` field pointing at a bookmark, a table of contents
is a `TOC` field, a page number is a `PAGE` field. An edit that rebuilt a
paragraph dropped them and `check --against` reported nothing, since it counted
neither.

- **`FID015`, a bookmark of the source is gone.** ERROR when a `REF`, `PAGEREF`
  or `NOTEREF` field of the edited file still points at it, where Word prints
  "Error! Reference source not found." or "Error! Bookmark not defined." when
  fields update. WARN when only an internal link still points at it, and WARN
  when nothing does and its name does not start with `_`. A hidden bookmark
  nothing points at, such as `_GoBack`, is not reported.
- **`FID016`, fields of the source are gone**, per story and kind. ERROR for a
  lost `REF`, `PAGEREF` or `NOTEREF`, even when others remain, and for any
  other kind when none of it is left in the story; else WARN. A field pointed
  at another bookmark counts as gone.
- **What a field is.** Its kind and, for `REF`, `PAGEREF` and `NOTEREF`, the
  bookmark it points at. Switches are not compared, because LibreOffice
  rewrites them on every save, and a field inside another field's result, such
  as the `PAGEREF` of each entry of a table of contents, is not counted.
  Headers and footers are counted per effective slot; a `HYPERLINK` field that
  became a `w:hyperlink` element is not a loss.
- **`FID001`/`FID002` count two more constructs:** endnote references (ERROR
  when lost, like footnote references) and section breaks (WARN; ERROR when
  all are lost, as for every construct).

On the [public corpora](../real-world-corpora.md) the new findings report none
of 1,841 files against themselves and none of 1,816 python-docx saves; 188 of
278 files after `paragraph.text` was assigned where a field or bookmark stood,
the other 90 having lost nothing the rules compare; and 38 of 385 LibreOffice
saves, each of their 54 findings for a field, bookmark or section break the
save did change. No save by Word of a document with fields was measured
([scope, corpus run and limits](../../evidence/docx-references/README.md)).

## MCP catalogs

- [`server.json`](../../server.json) describes the server in the MCP Registry
  format as `io.github.Dmitry-Kov/ooxml-integrity`: the PyPI package, started
  with the argument `mcp`, over stdio. The README carries the `mcp-name:` line
  the registry looks for in the README published on PyPI, so 0.10.0 is the
  first version that can be listed; 0.9.0 and earlier cannot. Listing follows
  publication and is the registry's to confirm ([catalogs](../mcp.md#catalogs)).
- The server itself changes only by the optional `introduced` argument of
  `compare`. It is still a local process that opens no socket.

## Compatibility

A pinned 0.9.0 job can change its result in these cases:

- **A document that passed can exit 1** when one comment id has a second range
  start, range end or reference in one story (`CMT007` ERROR). It belongs to
  the coverage item `docx.comments`; its baseline v2 identity is file, code and
  the story part, as for `CMT001`–`CMT004`.
- **A comparison that passed can exit 1** when the edit lost a bookmark that a
  `REF`, `PAGEREF` or `NOTEREF` field still points at (`FID015` ERROR), such a
  field itself, or every field of another kind in a story (`FID016` ERROR), an
  endnote reference, or every section break (`FID001` ERROR).
- **A `--fail-on warn` comparison that passed can exit 1** as well when the
  edit lost a bookmark only a link or nothing points at (`FID015` WARN), some
  fields of a kind other than those three (`FID016` WARN) or some section
  breaks (`FID001` WARN), and a `--fail-on info` comparison when the edit added
  an endnote reference or a section (`FID002` INFO).
- An intended removal is declared as an
  [expectation](../configuration.md#changes-the-edit-was-asked-to-make), for
  example `--expect FID016:story=document,kind=TOC`. `--introduced` never sets
  the new fidelity findings aside. In a baseline, `FID015` is identified by its
  names and `FID016` by story, kind, count and targets, each hashed.
- Without `--introduced` no report changes. With it, the JSON report gains an
  optional top-level `introduced: true`, absent otherwise; the suppressed
  entries have the shape config and baseline suppressions have.
- No baseline migration is needed. A baseline written by 0.9.0 is read as
  before; an existing file with one of the new findings needs
  `--write-baseline` again after review, or the finding fixed.
- Other rule codes, severities, report fields, coverage schema 1, Doctor schema
  1, SARIF 2.1.0 and CLI exits are those of 0.9.0. JSON/Doctor package version
  becomes `0.10.0`. See the [compatibility policy](../compatibility.md).

2993 tests with 7 documented skips on Python 3.12, the suite run from the
unpacked sdist (2965 passed, 35 skipped), the 220-pair producer corpus, 30
revision pairs and 168 stored editor output pairs, the frozen checker replay,
the four comment-story pairs, reference-deck assertions, a rerun of the
anonymize measurement with the same result, strict wheel/sdist metadata checks
and both fresh installations, plus all 7 real Chromium/Pyodide scenarios
against the exact local candidate wheel. The local run on Python 3.14 that
earlier candidates had was not made: the preparing machine has no 3.14

end and reference are written twice, `--introduced` setting aside what the
source already had from the CLI, Python and the MCP server but not a new repeat
or lost content, `FID015` for a lost bookmark a `REF` field points at and
`FID016` for that field written as text. On 0.9.0 the same inputs give no
finding, and `--introduced` is not an argument. No new Office, agent or model
run was part of release packaging. Local candidate and later publication hashes
are separate records.
