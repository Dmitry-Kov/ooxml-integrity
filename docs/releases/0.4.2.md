# ooxml-integrity 0.4.2 candidate

Prepared for review; no `v0.4.2` tag or PyPI publication yet. This candidate
collects the merged DOCX pilot fixes and two bounded revision-loss checks.
Python 3.9+, dependencies and the MIT license are unchanged. The project remains
research-alpha; preservation of OOXML structure is not visual equivalence.

## Changes that can affect a gate

| Change | Affected comparison and possible result |
| --- | --- |
| New `FID009` ERROR | Simple main-document insertion/deletion text disappears while same-kind wrapper counts stay equal: previously clean comparisons can exit 1. Literal wording is checked, not revision identity. |
| New `FID010` ERROR | An equally populated, nonempty footnote/endnote text group retains fewer notes with insertion/deletion markup: previously clean comparisons can exit 1. This checks presence per note and kind. Unexpected conventional note-part roots now prevent comparison with `FID000`. |
| `FID001` coalescence fix | Word can merge plain inline revision fragments without losing their text/author/effective time/direct formatting/paragraph position. A strict ordered witness now permits those lower counts, potentially changing exit 1 to 0. Unsupported structures keep the conservative count check. |
| Comments relationship resolution | Renamed main-document comment parts no longer cause false `CMT004`/`FID004`; actual body loss there is detected. New `CMT006` ERROR flags invalid, ambiguous or unreadable targets. Unresolvable source comparisons remain `FID000`. `REL002` accepts ASCII case-equivalent package targets. |
| `TXT001` and CLI serialization | XML whitespace and inherited `xml:space` are respected; NBSP alone no longer causes a warning. Warning locations avoid quadratic sibling scanning. Legacy stdout encodings such as cp1252 now serialize JSON losslessly with escapes, and human output escapes unencodable characters instead of crashing. |

See the protocols and counterexamples for [FID009](../../evidence/docx-revision-text/README.md),
[FID010](../../evidence/docx-note-revisions/README.md),
[FID001](../../evidence/docx-fid001-coalescence/README.md) and
[pilot fixes](../../evidence/adeu-pilot-followup/README.md).
`REV001` is unchanged. Intentional accept/reject operations can still trigger
preservation findings; authorization cannot be inferred from the output alone.

## Compatibility and limits

CLI exits remain 0 / 1 / 2; SARIF remains 2.1.0 and coverage/Doctor schema remains
1. JSON and Doctor identify package version `0.4.2`. Consumers must tolerate the
new codes and additive `docx.fidelity.revision-text` and
`docx.fidelity.note-revisions` coverage identifiers. Baseline v2 remains readable;
no migration is required from 0.4.1. Review new findings and actual renamed-part
locations before accepting a changed baseline. Baseline v1 is still rejected.

FID009 skips unsupported structures, changed counts and bounded-search omissions;
incidental repeated wording can mask loss. FID010 skips empty/changed note groups
and can miss partial removal within a note or reassignment across identical note
text. Neither rule establishes full revision identity, metadata/formatting
preservation, relocated-note support or visual sameness. See the
[support matrix](../support-matrix.md) and [coverage contract](../coverage.md).

## Candidate verification and publication boundary

The separate [candidate validation record](../../evidence/releases/0.4.2/README.md)
contains commands, environment versions, current corpus receipts and local
artifact hashes. Historical reports and input/output hashes are retained.
Rechecking saved pairs is not a new editor or model run; seeded defects are
reported separately from real saves/edits. The 220-pair producer corpus is a
regression set, not an editor ranking or a general recall estimate.

The distribution smoke now verifies installed source bytes against the release
checkout and exercises FID009/FID010 plus their coverage, alongside existing
CLI/JSON/SARIF/baseline/config contracts. The wheel is built from the sdist and
tested in an isolated Chromium/Pyodide preview. The public demo and working
consumer examples remain pinned to published 0.4.1.

After merge, successful CI on the exact `main` commit, the public Action-tag
checks and post-publication PyPI installation/hash checks are still required.
Preparing this candidate does not run those publication gates. Follow the
[release procedure](../releasing.md); update this candidate status only after
publication is verified.

These pins are for use **after** the version/tag is published:

```sh
python -m pip install --upgrade ooxml-integrity==0.4.2
python -m ooxml_integrity --version
```
