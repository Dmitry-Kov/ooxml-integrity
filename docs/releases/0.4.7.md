# ooxml-integrity 0.4.7

Release candidate for four changes found by the review-history benchmark
(waves 1 and 2, with a native Word for Mac check) and by a crash test: two new
warnings for damage 0.4.6 did not report, an `INT001` that now fails the run,
and fewer false losses for tracked edits next to pending revisions. Publication
is pending the release workflow; current consumer/demo examples remain pinned to
published 0.4.6 during preparation. Python 3.9+, dependencies and the MIT
license are unchanged. The project remains research-alpha.

## Gate changes and limits

These changes can turn a passing run into a failing one:

- `INT001` (a check raised) is an ERROR instead of a WARN (#46). A crashed check
  used to pass the default error gate with exit 0 while `--coverage` still
  reported its surface as `checked`. The finding now names the check and the
  exception type (`extra.check`, `extra.exception`), that check's coverage items
  are `skipped`, and the other checks still run. A baseline never records or
  absorbs `INT001`; a known crash can be turned off with a config `ignore` and its
  reason, or a severity override. None of the 1,050 DOCX/PPTX files committed to
  this repository produces it.
- `TXT002` (WARN) reports text or a list label that still reads like `&#8226;`
  after XML decoding (#43). docx-cli 0.26.0 writes S1's bullet labels as
  `&amp;#8226;`, and Word for Mac shows the literal `&#8226;` in place of each
  bullet. Only references to punctuation and symbol characters count, because a
  document about XML can quote one on purpose.
- `FID011` (WARN, with a source) reports text added inside another author's
  pending insertion without a tracked insertion of its own (#43), which Word
  shows as that author's insertion. Insertions are grouped by author and date,
  and the old text must survive intact and in order; a same-author continuation
  with the same date cannot be told apart. The new coverage item
  `docx.fidelity.insertion-attribution` counts the insertions compared and says
  why the others were skipped.

Both warnings fail only `--fail-on warn` gates or configured overrides; the
default error gate is unaffected by them. [Scope and limits](../review-edit-warnings.md).

This change removes findings and can change exit 1 to 0:

- `FID004`-`FID007` also accept a tracked edit to a comment, note or
  header/footer that already had pending revisions (#40). In the benchmark the
  reference control's correct tracked edit to S2's header, next to Reviewer A's
  pending change of the draft number, was reported as a lost story. The item now
  matches when the edited item, with every revision the source item did not have
  rejected, holds the same characters under the same pending revisions (kind,
  author and date). Accepting, rejecting or re-dating a pending revision, or an
  untracked change, is reported as before.

On the public corpora nothing changes: 2,497 files give the same findings as
0.4.6, 1,819 python-docx no-op pairs give none, and the `mutate` edits detect
33/33 revision, 42/42 footnote and 40/40 comment losses with no careful edit
flagged.

What the benchmark still shows: on correct edits 0.4.7 keeps the false alarms
for requested accept/reject (`FID001`), untracked header and note edits
(`FID007`/`FID005`) and a requested direct edit inside another author's
insertion (`FID009`). The checker has no way yet to be told which changes were
intended. See the [benchmark](../../evidence/review-history-benchmark/README.md).

## Compatibility

Two rule codes are added (`TXT002`, `FID011`) and one severity changes (`INT001`
WARN to ERROR). Coverage schema 1 gains two additive items
(`docx.literal-entities`, `docx.fidelity.insertion-attribution`). `FID011`
baseline v2 identities hash the author, date, source text and added text.
Report fields, Doctor schema 1, SARIF 2.1.0, CLI exits 0/1/2 and the other
baseline v2 identities are unchanged; an obsolete baseline entry for a finding
that no longer occurs may remain unused. JSON/Doctor package version becomes
`0.4.7`. See the [compatibility policy](../compatibility.md).

## Validation and publication

[Candidate validation](../../evidence/releases/0.4.7/README.md) passed:
2147 tests with 7 documented skips, on Python 3.12 and 3.14, the 220-pair
producer corpus, 30 revision pairs and 168 stored editor output pairs, the
frozen checker replay, the four comment-story pairs, reference-deck assertions,
strict wheel/sdist metadata checks and both fresh installations, plus all 7 real
Chromium/Pyodide scenarios against the exact local candidate wheel. The
installed-package smoke adds the 0.4.7 controls: a tracked header edit next to a
pending revision, `TXT002`, `FID011` and `INT001`. No new Office, agent or model
run was part of release packaging. Local candidate and later publication hashes
are separate records.

After candidate checks pass, CI must pass on the exact merged main commit before
tagging. The Release workflow then verifies the remote pinned Action, rebuilds
and tests distributions, publishes those files to PyPI, and creates the GitHub
Release. Public PyPI installation/hash verification and consumer/demo pin updates
follow publication. See [release procedure](../releasing.md).

Use these pins **after publication**:

```sh
python -m pip install --upgrade ooxml-integrity==0.4.7
python -m ooxml_integrity --version
```

```yaml
- uses: Dmitry-Kov/ooxml-integrity@v0.4.7
  with:
    files: "out/**/*.docx"
    against: templates/master.docx
    fail-on: error
```
