# ooxml-integrity 0.9.0

Published 2026-11-02T16:18:22Z on [PyPI](https://pypi.org/project/ooxml-integrity/0.9.0/)
and as a [GitHub Release](https://github.com/Dmitry-Kov/ooxml-integrity/releases/tag/v0.9.0). The package rules of
`.docx` run on `.pptx` decks, each message saying what PowerPoint does, and a
namespace name that is not a URI, as SharePoint writes into custom XML parts,
is no longer malformed XML. A deck that passed can now fail, hence the minor
version. Python 3.9+, dependencies and the MIT license are
unchanged. The project remains research-alpha.

## `.pptx` packages

- **The package rules run on decks.** Through 0.8.4 `check_pptx` read only what
  its layout checks need: `ppt/presentation.xml` by its name, the slides it
  lists and their layouts, masters and themes. A deck without
  `[Content_Types].xml` or `_rels/.rels`, with a declaration written twice or a
  relationship to nothing, was reported clean. `XML001`, `PKG003`–`PKG005`,
  `PKG011`, `PKG012`, `REL001`, `REL002` and `REL004` now run on decks.
  PowerPoint for Mac 16.114.3 refused every variant of a PowerPoint-saved deck
  whose defect Word refuses, and opened nothing on **Cancel**; it opened every
  variant Word opens ([PowerPoint check](../../evidence/pptx-package-rules/README.md)).
- **The messages say what PowerPoint does**: "PowerPoint asks to repair the
  presentation", and for a reference to a relationship the part lacks
  (`REL001`), "or shows the object as missing": PowerPoint refused such a
  hyperlink and drew such a picture as one it can't display. It drew a picture
  whose relationship targets a missing part the same way; that stays a
  `REL002` ERROR.
- **A missing thumbnail or SmartArt drawing is a `REL002` WARN.** PowerPoint
  opened LibreOffice decks with either and drew SmartArt from its data.
- **Word's own rules do not run on decks.** `PKG006`, `PKG009`, `PKG010` and
  `REL003` read Word's main part or relationship types. A Strict deck is still
  `PKG009`, and an archive that cannot be read is reported as before.

Of 610 public decks, findings change in 22, only by additions: 5 get an ERROR
(`PKG005`, `PKG012`, `REL001`, `REL002`), each of which PowerPoint refused, and
17 a WARN: 15 `PKG004` for relationship parts declared by `Override`, and
`REL002` for a missing thumbnail or SmartArt drawing
([public decks](../real-world-corpora.md#pptx-package-rules-090)). The decks of
this repository are unchanged.

## XML

- **A namespace name that is not a URI.** SharePoint document libraries write
  `xmlns:ns3="$ListId:Shared Documents;"` into custom XML parts. libxml2 2.14
  reports such a name at error level, so `XML001` called a well-formed part
  not well-formed (ERROR). Word and PowerPoint for Mac open such packages
  without a prompt ([Word and PowerPoint check](../../evidence/xml-namespace-names/README.md)).
  A part whose parse reports nothing else is now read; any other error still
  fails it, and a `DOCTYPE` is still refused. No file of the public corpora or
  this repository changes.

## Compatibility

- `check_pptx`, and `check` on a deck, report the package rules, so a deck that
  passed the default gate can exit 1. The coverage item
  `pptx.package-integrity` is `checked` (`skipped` when a package check fails
  with `INT001`) instead of `unsupported`, and `doctor` no longer lists it as
  unavailable. Baseline v2 identities are the general ones.
- A deck the layout checks cannot read still ends with `PKG002`; the package
  findings, such as `XML001` for the slide that is not well-formed, come
  before it.
- A part whose only parse error is a namespace name that is not a URI no
  longer gets `XML001`, so a document or deck that failed can exit 0.
- Other rule codes, severities, report fields, coverage schema 1, Doctor schema
  1, SARIF 2.1.0 and CLI exits are those of 0.8.4. JSON/Doctor package version
  becomes `0.9.0`. See the [compatibility policy](../compatibility.md).
