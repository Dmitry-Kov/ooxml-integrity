# ooxml-integrity 0.4.8

Published 2026-10-03T06:16:50Z on [PyPI](https://pypi.org/project/ooxml-integrity/0.4.8/)
and as a [GitHub Release](https://github.com/Dmitry-Kov/ooxml-integrity/releases/tag/v0.4.8). A caller can now declare the
findings an edit was asked to cause, so a requested change stops failing the
run and a requested change that did not happen does. Python 3.9+, dependencies
and the MIT license are unchanged. The project remains research-alpha.

## Expected changes

Accepting or rejecting a named revision lowers the revision count (`FID001`),
an untracked header rewrite changes that story (`FID007`), an untracked note
edit changes its body (`FID005`). Until now such a correct edit failed
`compare()` the same way damage does, and a pipeline that makes it on purpose
had to switch the rule off, which also hides the header it was never asked to
touch.

- `--expect CODE:key=value,...` on the command line, `[[expect]]` in the
  config (with a required `reason` and an optional `path` glob) and
  `expect(findings, expectations)` in Python declare such a finding. It is
  matched on `part`, `where` or any key of its `extra`, compared as text.
- A matching finding is listed as expected, with its reason, and does not fail
  the run. An expectation that matches nothing in a file it applies to is a new
  `EXP001` ERROR: the requested change did not happen, or not the way it was
  declared. `required = false` allows a finding without requiring it.
- The JSON report lists matched findings under a per-file `expected` key, only
  when expectations are declared. SARIF marks them suppressed with the reason.
  A baseline never records or absorbs `EXP001`.

An expectation states which change is allowed, not what the result must look
like: `FID007` for a header accepts any change to that header's text.
[How to declare them](../configuration.md#changes-the-edit-was-asked-to-make).

Re-reading both waves of the [review-history benchmark](../../evidence/review-history-benchmark/expectations/README.md)
with expectations derived only from each task's declaration: of 537 correct
outputs, 130 were flagged and 12 still are, all true reports outside the
oracle's scope (replies with no document anchor, a repeated revision id, an
undefined style). Of 69 damaged outputs, 59 were caught and 63 are: tools that
edited the document title instead of the requested header now fail with
`EXP001`. No caught damage is lost and no correct output gains `EXP001`.

Without expectations nothing changes: rule codes, severities, messages, report
fields and baseline identities are those of 0.4.7, and the public corpora give
the same findings on all 2,497 files.

## Compatibility

One rule code is added, `EXP001`, raised only when expectations are declared.
The JSON report gains the additive per-file `expected` list under the same
condition. Config files may contain an `expect` key; earlier versions reject
it as unknown. Coverage schema 1, Doctor schema 1, SARIF 2.1.0, CLI exits
0/1/2 and baseline v2 identities are unchanged. JSON/Doctor package version
becomes `0.4.8`. See the [compatibility policy](../compatibility.md).
