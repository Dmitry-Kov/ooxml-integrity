# ooxml-integrity 0.4.9

Release candidate for one addition: `compare()` lists the tracked changes an
edit added, per story, kind and author, so a caller can require a tracked edit
in the story it was asked for. Publication is pending the release workflow;
current consumer/demo examples remain pinned to published 0.4.8 during
preparation. Python 3.9+, dependencies and the MIT license are unchanged. The
project remains research-alpha.

## Tracked changes added (`FID012`)

A correct tracked edit loses nothing, so until now nothing distinguished it
from the same tracked edit made in the wrong place. In the review-history
benchmark docxengine was asked to change the header with tracked changes,
edited the document title instead, and passed.

- `FID012` (INFO) is one finding per story, kind and author of tracked changes
  the edit added. Stories are `document`, each effective header/footer slot
  (`header/default`, `footer/first`, ...), `footnotes` and `endnotes`. A
  revision is new when no revision in the source story had the same kind,
  author and effective date (`w16du:dateUtc` before `w:date`), so splitting or
  joining an existing revision adds nothing. An edit stamped with an existing
  revision's author and date is not listed; comments' revisions are not read.
- With 0.4.8's expectations it says where a tracked edit landed:

  ```toml
  [[expect]]
  code = "FID012"
  reason = "the pipeline revises the header as Benchmark Editor, tracked"
  match = { story = "header/default", author = "Benchmark Editor" }
  ```

  A tracked edit made elsewhere leaves this unmatched and fails with `EXP001`.

Reading the review-history benchmark again with this expectation for every
tracked replacement, on top of 0.4.8's: of 537 correct outputs 12 are still
flagged, all true reports outside the oracle's scope, and no correct output
gains `EXP001`; of 69 damaged outputs 65 are caught instead of 63, the two
added being docxengine's title-instead-of-header edit in both captures.
[Analysis](../../evidence/review-history-benchmark/expectations/README.md).

On the public corpora the python-docx no-op and mutation results are those of
0.4.8.

The support matrix also records two limits, measured on the public corpora:
styles, numbering, notes and comments parts are still read under their
conventional names, and none of 1,851 readable DOCX files names them otherwise;
constructs inside notes are not compared with the source, and three or four of
582 files with footnotes hold any, none a comment anchor.

## Compatibility

`FID012` is a new INFO finding; it never fails the default gate. A
`--fail-on info` gate that compares a tracked edit already failed on `FID002`
for body edits and now also fails on header, footer and note edits. Its
baseline v2 identity hashes the story, kind and author, not the count. Other
rule codes, severities, messages, report fields, coverage schema 1, Doctor
schema 1, SARIF 2.1.0, CLI exits 0/1/2 and baseline v2 identities are those of
0.4.8. JSON/Doctor package version becomes `0.4.9`. See the
[compatibility policy](../compatibility.md).

## Validation and publication

[Candidate validation](../../evidence/releases/0.4.9/README.md) passed:
2180 tests with 7 documented skips, on Python 3.12 and 3.14, the 220-pair
producer corpus, 30 revision pairs and 168 stored editor output pairs (with the
80 declared `FID012` additions), the frozen checker replay, the four
comment-story pairs, reference-deck assertions, strict wheel/sdist metadata
checks and both fresh installations, plus all 7 real Chromium/Pyodide scenarios
against the exact local candidate wheel. The installed-package smoke adds the
0.4.9 controls: `FID012` for tracked body, header and S2 edits, and an
expectation on it that fails a tracked edit in the wrong story. No new Office,
agent or model run was part of release packaging. Local candidate and later
publication hashes are separate records.

After candidate checks pass, CI must pass on the exact merged main commit before
tagging. The Release workflow then verifies the remote pinned Action, rebuilds
and tests distributions, publishes those files to PyPI, and creates the GitHub
Release. Public PyPI installation/hash verification and consumer/demo pin updates
follow publication. See [release procedure](../releasing.md).

Use these pins **after publication**:

```sh
python -m pip install --upgrade ooxml-integrity==0.4.9
python -m ooxml_integrity --version
```

```yaml
- uses: Dmitry-Kov/ooxml-integrity@v0.4.9

```
