# Review-history benchmark — protocol

Declared on 2026-09-30, before any benchmarked tool ran. [protocol.json](protocol.json)
pins this file, the task file, the sources, the oracle, task, evaluator,
reference and adapter scripts, and the checker release. Later waves add
adapters under their own declarations; this text does not change for them.

## Question

When a tool makes an ordinary edit to a DOCX that already carries comments,
other authors' pending revisions and notes, what survives the edit, what is
lost or broken, and does `ooxml-integrity` report it?

Two results are kept apart: a preservation matrix (tool × task → facts lost)
and detection (for each loss, whether the checker reported it; for each output
without a loss, whether it raised a false alarm). Numbers describe this corpus
only. Not goals: ranking tools, layout and rendering, formatting outside a
tracked formatting change, model quality.

## Tasks

[tasks.json](tasks.json) is generated by `research/review_history_tasks.py`,
which checks each target against its source and computes every expected text.
Each entry has a structured `call` for deterministic tools and a `prompt` for
agents; both describe the same edit.

| Task | Edit | At risk |
| --- | --- | --- |
| K0 | open and save, no edit | serialization |
| K1 | replace a phrase inside a commented range | the comment's anchor |
| K2 | replace the value of a table cell that carries a comment | cell comment anchor |
| K3 | edit the sentence that holds a footnote reference | the reference |
| K4 | edit inside another author's pending insertion (S2: next to a third author's nested deletion) | other authors' revisions, nesting |
| K5 | reply to an existing comment and add a new comment | threads, `commentsExtended`, people |
| K6 | accept one named revision, reject another, keep the rest | selective resolution |
| K7h | edit the page header (S2: next to a pending revision there) | revisions outside the body |
| K7n | edit a footnote's text | note bodies |

Replace tasks run in two modes when the tool offers both: `tracked` (a tracked
change by `Benchmark Editor`, initials `BE`, date `2026-10-01T00:00:00Z` where
the tool can set it) and `plain` (a direct edit). A direct edit inside another
author's pending insertion stays inside that insertion, so the paragraph's
rejected text is unchanged in both modes. 30 declarations in all.

A tool without the operation gets status `unsupported`, which is not a
preservation failure. Two captures per deterministic adapter; five per agent
and task. Every attempt starts from its source, never from a prior output.

## Evaluation

Four axes, recorded separately. A pass needs all of the first three.

1. **Status**: `ok`, `unsupported`, `rejected` (the tool refused), `error` or
   `timeout`, with the tool's own message.
2. **Task completed**, judged on the output's XML:
   - replace: the target paragraph's current (accept-all) and original
     (reject-all) texts equal the declared ones. In tracked mode the output has
     at least one new revision by the editor in that paragraph and none
     elsewhere; in plain mode it has no new revision.
   - K5: a comment with the reply text is linked to the named comment through
     `w15:paraIdParent`, and a new comment's anchor covers exactly the phrase.
   - K6: the named revisions are gone, the texts are as declared, and every
     other revision is still present.
   - K0: nothing to complete.
3. **Preserved**: the oracle's report from source to output
   (`research/review_history_oracle.py`, dates compared), minus what the task
   declares. Anything left is a preservation failure, listed by fact category.
   Inside the target paragraph, revisions are judged character by character
   over all of its text, deleted or not, with each character's revision
   wrappers (kind, author, date) and its run's formatting revision. In tracked
   mode, removing the editor's insertions and the editor's wrappers from the
   output must give the source exactly, and the editor may delete only inside
   the old text. In plain mode, the output must be the source with exactly the
   old text replaced by the new text, which takes the old text's wrappers.
   The paragraph's own revisions (its mark and property changes) must remain.
   Outside it, the task may change:
   - the target paragraph's texts, to the declared ones; in plain mode, the
     paragraph context recorded on other facts in that paragraph (comment
     anchors, note references, list items, and the cell or content control
     that holds it) changes with it;
   - the current text of comment anchors inside the target paragraph (and, in
     plain mode, their original text), not their existence or markers;
   - for K7, the story or note facts of the edited header or note;
   - for K6, the named revisions (lost) and the texts of their paragraphs;
   - additions by the editor: revisions in the target paragraph (tracked
     mode), the K5 comments with their thread, date, resolution and durable id,
     and a `people.xml` entry.

   Pre-existing dates must be unchanged. Package parts that disappear are
   failures; parts that change or are added are recorded as package changes,
   not failures, since serialization and formatting are out of scope.
4. **Checker**: `ooxml-integrity` 0.4.6 (the release with the tracked-edit
   correction), `check(output)` plus `compare(source, output)`, no
   configuration, recorded in full. Primary, per output: an output with a
   preservation failure is detected if the checker reports any ERROR or WARN
   that the source did not; an output without one is a false alarm if it does.
   Secondary, per failure category, a declared mapping to the rules that
   concern it (revisions: `FID001`, `FID009`, `FID010`, `REV*`; comments:
   `CMT*`, `FID004`; notes: `FID005`, `FID006`, `FTN*`; headers/footers:
   `FID007`, `FID008`; content controls, tables, hyperlinks, images and lists:
   `FID001`; paragraph text: `FID003`). "0 findings" is never a quality score.

## Isolation and capture

The first wave runs two python-docx 1.2.0 adapters from
`research/review_history_adapters.py` and the reference control from
`research/review_history_reference.py`. python-docx has no tracked changes,
comment replies or note API: tracked replacements, K6 and K7n are
`unsupported`, and for K5 it adds only the new comment, on the whole run that
holds the phrase. `python-docx-setter` is the tutorial and MCP-wrapper path
(`Paragraph.text =`, `_Cell.text =`); `python-docx-runs` is the careful path
(`Run.text =` on the runs that hold the old text). The reference control
performs every task on the XML the way Word records it; it shows that a pass
is reachable and is not scored as a tool.

The checker runs in a separate environment installed from the exact public
0.4.6 wheel (SHA-256 `7194485c…`), never from the checkout.

Later third-party tools each run in their own Docker image: base image by digest,
versions and lock files pinned, network only while building. Runs use
`--network none --user 65534:65534 --cap-drop ALL --security-opt
no-new-privileges -e HOME=/tmp`, with only the source (read-only) and an output
folder mounted. Every new tool needs Dmitry's explicit approval before its
first run. python-docx is already in the development environment and runs
there.

As in the earlier benchmarks: `protocol.json` pins the hashes of the sources,
`tasks.json`, this protocol, the oracle and task scripts, the adapters and
images, and the checker version; `started.json` is written before the first
call; each attempt gets a receipt created exclusively; `capture.json` closes
the run; `verify` fails on any drift. CI re-evaluates frozen outputs only and
never runs a tool.

Each class of loss found gets one representative output opened in Word for
Mac. Confirmed losses get a minimal reproduction and a draft upstream issue,
published only after approval. Results are stated as "operation X in version Y
loses Z", without rankings.
